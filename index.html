La mesa de negociación de cotizaciones, hecha software.

QUOTIA digitaliza el ciclo completo de una solicitud de cotización de granos —desde el borrador hasta la adjudicación— con negociación configurable, reglas de negocio propias, estados auditables y aislamiento por corredora. No es un tablero de pedidos: es la mesa de negociación, gobernada por software.

El negocio

Una corredora pide. Las contrapartes cotizan. Alguien se adjudica.

Ese es el ciclo de una RFQ (Request for Quotation) de cereales. QUOTIA lo modela paso a paso, con contexto agro argentino: soja, maíz y trigo; puertos como San Lorenzo o Bahía Blanca.

01 · EMISOR

Solicitud

La corredora arma una solicitud desde una plantilla: define ítems (renglones) y atributos (calidad, cantidad, puerto, condición de pago). Vive como borrador hasta publicarse.

02 · CONTRAPARTE

Cotización

Publicada la solicitud, las contrapartes ingresan sus ofertas por ítem. Cada campo se valida contra su tipo de dato: un precio o una cantidad no pueden ser cero ni negativos.

03 · MESA

Negociación

Oferta y contraoferta, turno a turno. El sistema controla completitud, campos requeridos y atomicidad: un turno se aplica entero o no se aplica. Con vigencia y vencimiento por reloj.

04 · EMISOR

Adjudicación

El emisor concierta: acepta formalmente precio y condiciones de una línea. La negociación cierra concertada, declinada o vencida —y todo el recorrido queda auditado.

FLEX

Plantillas

Cada solicitud hereda su forma de una plantilla configurable: qué atributos existen y cuáles son requeridos, heredables o negociables. Versionadas, para no romper lo ya publicado.

AUDIT

Trazabilidad

Cada cambio de estado y cada turno dejan rastro. El estado real de una negociación nunca se sobrescribe —se explica— lo que hace todo el proceso reconstruible.

Qué incluye

Una plataforma completa, no solo un formulario de pedidos.

QUOTIA cubre todo lo que una corredora necesita para operar: desde configurar su catálogo de negocio hasta cerrar una adjudicación. Estos son los módulos que ya usan las corredoras.

Solicitudes

Alta, edición y publicación de solicitudes con ítems y atributos. Filtros por cuenta y estado, borradores y ciclo de vida completo.

Operación

Mesa en vivo con dos vistas: emisor y contraparte. Oferta, contraoferta, pausa, cierre y adjudicación, turno a turno, con vigencia por reloj.

Operación

Cada contraparte ve solo las solicitudes en las que participa y arma su propuesta desde su propia sala, sin ver al resto del mercado.

Seguridad

Usuarios y roles

Usuarios por cuenta con roles y permisos granulares. Cada acción del sistema se autoriza según el rol —nada queda librado al azar.

Segmentación y roles

Cada corredora ordena su operación a su manera.

QUOTIA no impone una única forma de trabajar. La corredora segmenta su universo de productores y contrapartes por los ejes que le sirven, y le da a cada persona exactamente el acceso que le corresponde.

Rol · Configura

Administrador

Gobierna el tenant: define plantillas, atributos, catálogos, rubros, carteras y usuarios. Deja lista la cancha para que el resto opere. Es quien traduce el negocio de la corredora al sistema.

Rol · Opera

Oficial de cuenta

El corredor que trabaja el día a día: publica solicitudes por las cuentas que tiene asignadas, conduce las negociaciones y adjudica. Ve y opera solo lo suyo.

Rol · Participa

Contraparte

El productor o comprador del otro lado de la mesa. Cotiza y contraoferta desde su bandeja, sin acceso a la operación interna ni al resto del mercado. Ve únicamente lo que se le compartió.

Ejes de segmentación

◆

Por cartera

Agrupá productores y contrapartes en carteras y asigná qué oficial las trabaja. La cartera define el recorte de mercado de cada corredor.

▲

Por cuenta

La cuenta activa fija el contexto: un usuario opera dentro de una cuenta por vez, y solo ve solicitudes y negociaciones de esa cuenta.

●

Por rubro y etiqueta

Clasificá el negocio por rubro (tipo de operación) y por etiquetas propias, para que cada quien encuentre y trabaje su segmento.

Ventaja competitiva

La diferencia está en la negociación.

La mayoría de las plataformas de RFQ terminan cuando llegan las ofertas: recibís cotizaciones y elegís. QUOTIA empieza justo ahí. La negociación es configurable, con reglas de tu negocio, y auditada de punta a punta.

◇ NEGOCIACIÓN

Contraoferta real, no solo cotizar

Oferta y contraoferta turno a turno, con vigencia, pausa y cierre. Un RFQ convencional recibe precios; QUOTIA sostiene la ida y vuelta hasta el acuerdo.

◇ A MEDIDA

Reglas de tu negocio

Qué atributos se negocian, cuáles son requeridos, qué debe ser positivo, cómo heredan las plantillas. La lógica se configura —no viene enlatada e inmodificable.

◇ CONFIABLE

Atómico y auditado

Cada turno se aplica entero o no se aplica. Cada cambio de estado deja rastro. El estado real nunca se pisa: se explica. Reconstruís cualquier negociación.

La arquitectura

Un motor en la base, una API que lo gobierna.

El estado y las reglas viven en PostgreSQL. Ningún cliente toca la base directo: todo pasa por la API FastAPI, que resuelve el tenant, valida y persiste vía RPCs. Ese contrato es lo único que un cliente necesita conocer.

Los clientes nunca hablan con Supabase directo — el frontend consume la API vía apiClient. La base es del backend.

Multi-tenant real

Cada corredora es un tenant aislado. La API resuelve a qué esquema apuntar según el JWT y fija el search_path: los datos de una corredora nunca se cruzan con los de otra.

EAV — campos que cambian

No todas las solicitudes tienen los mismos campos. El modelo entidad-atributo-valor deja que cada plantilla defina sus atributos, y valida que cada valor caiga en el campo correcto según su tipo de dato.

La máquina de estados

Tres niveles que se mueven juntos.

Una solicitud contiene negociaciones; una negociación, ítems. Cada nivel tiene su propio estado, y el sistema los mantiene coherentes. Estos son los estados reales del modelo.

Regla — estado virtual

El estado real de una negociación o un ítem nunca se pisa. Si la solicitud padre se cierra o pausa, el hijo no se reescribe: se refleja como Cerrada (por solicitud) o Pausada (por solicitud). La verdad de cada nivel se conserva; el efecto del padre se explica, no se destruye.

Extensibilidad

Otro front o un mobile se enchufan sin tocar la base.

Como toda la lógica vive en la API y en la base, el contrato con el sistema es la API REST —no el esquema de Postgres. Cualquier cliente que hable HTTP con un JWT válido es un ciudadano de primera: el front web de hoy, una app mobile mañana, o la integración de un tercero.

Por qué es barato sumar clientes

Cero lógica duplicada. Las reglas —validación, estados, atomicidad, aislamiento— viven una sola vez, en el backend. Un cliente nuevo no las reimplementa: las consume.

Mismo contrato, misma verdad. Web y mobile ven exactamente los mismos estados y las mismas reglas, porque preguntan al mismo lugar.

Autenticación uniforme. El JWT lleva el tenant; la API hace cumplir el aislamiento. Un tercero jamás ve datos de otra corredora.

Datos

PostgreSQL sobre Supabase

El motor central. Estado, reglas y persistencia atómica vía RPCs. Multi-tenant con aislamiento por esquema. Jobs programados con pg_cron para vencimientos.

FastAPI · Python

Expone REST, valida con Pydantic, maneja JWT y resolución de tenant, y orquesta la lógica de negocio. Python decide; SQL persiste. Es la única puerta a la base.
